# ユーザーの特殊条件を検証する

通常のサイト絞り込みや詳細ページの閲覧だけでは確実に判定できない条件が、今回の要件に含まれる場合のみ読む。特殊条件は今回のユーザー要件から決める。特定の都市、期限、事業者、暮らしの好みをあらかじめ組み込まない。

## 主エージェントが検証計画を決める

具体的な物件を割り当てる前に、主エージェントが特殊条件ごとに次の内容を決め、物件タスクとともに伝える。

- ユーザーが求める条件。必須条件か希望条件か、建物全体に適用するか具体的な部屋に適用するか、許容する基準値と例外を明確にする
- 確認すべき事実と合格条件。ユーザーの用語に複数の意味があり、意味によって絞り込み結果が変わる場合は、先にユーザーがどの意味で使っているかを確認する
- 質問に答えられる情報源と調べ方。運営側の検索、管理側の書面説明、図面、現地測定などについて、それぞれが証明できる範囲を示す
- 合格に十分な根拠、除外に十分な根拠、要確認としか記録できない根拠の違い。情報源同士の裏付けを必須とするかも定める
- 並行して実行できる独立した検索と、それぞれの入力・出力。ユーザーや主エージェントから補足が必要な情報、別途承認が必要な行為も示す

実行できる検証計画を作ってから、各物件の担当者に検証を求める。「条件を満たすことを確認」とだけ指示し、判断基準を担当者の推測に任せない。

方法や根拠の基準を変える必要がある場合は、主エージェントに判断を求める。決めた方法に沿った検証、再確認、通常の事実の相違の解消には、主エージェントが項目ごとに介入する必要はない。

## 物件検証担当者が計画を実行する

1. それぞれの根拠が、どの建物、部屋、条件に対応するかを明確にする。同名の建物、隣の建物、近隣施設、別室の根拠をそのまま流用しない
2. 計画に従って最新情報を調べ、情報源、検索日、対象範囲、重要な原文を残す。広告や販売宣伝の表現を、必要な技術上・契約上の事実の代わりにしない
3. ツールが使え、タスクが互いに独立している場合は、範囲を限定した確認をサブエージェントに任せてもよい。例えば、ある建物の利用可否を公式情報で確認するタスクが該当する。委任時は、確認済みの識別情報、質問、根拠の基準を伝える
4. 委任後も物件検証担当者が、識別情報の一致、根拠の統合、追加調査を担当する。情報源間・物件間の事実の矛盾が解決しない場合は、統合担当（merge resolver）に調整を依頼する。「専門的な確認を任せた担当者が可能と言った」を根拠の代わりにしない。専門的な確認の分担は、物件エージェントが自ら作成する物件全体の独立した再確認の代わりにはならない
5. 検索窓口が使えない、または公開情報が足りない場合は、質問に適した別の情報源を試す。それでも結論が出なければ、最小限の確認質問と、回答すべき相手を列挙する
6. 管理側への連絡、情報の提出、サービスの申し込みが必要なら、具体的な相手、行為、必要な承認を主エージェントに説明する。公開情報で調べられないことは、ユーザーの代わりに申し込んでよいという意味ではない

## 条件を判定し、調査結果を返す

| 判定する項目 | 基準と記録内容 |
|---|---|
| 合格 | ユーザーが定めた必要条件を、根拠ですべて確認できている。結論は、その根拠が適用される建物、部屋、時点、サービス範囲を超えない |
| 不合格 | 信頼できる根拠が、必須条件への不適合を明確に示している。不適合の項目を示す。検索結果がないことを利用不可と見なさない |
| 要確認 | 住所の一致が不確か、重要項目が欠落している、根拠が矛盾している、一部の条件しか証明できない場合。判断を終えるために何が足りないかを書く |
| 希望条件 | 適合の程度と理由を別記する。勝手に除外条件へ格上げせず、希望条件の長所で必須条件への不適合を相殺しない |

専門的な確認を任された担当者は、[contracts.md](contracts.md)の共通形式で物件担当者へ調査結果を返す。物件担当者は根拠を物件全体の調査結果に組み込み、自ら作成した独立した再確認エージェントに確認を依頼する。修正を終えてから統合担当へ渡し、最終結果にも未解決の特殊条件を残す。

## インターネット回線の要件がある場合

住宅のインターネット回線に関する要件がある場合のみ、[internet.md](internet.md)も読む。その他の特殊要件は、上記の方法で検証計画を作る。ネット回線の例があるからといって、標準で回線を確認したり、特定の接続方式を勧めたりしない。
