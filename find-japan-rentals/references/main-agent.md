# 主エージェント：条件と進行管理

## 条件と検証方法の整理

現在のユーザーの依頼と、明確に継続されている希望から条件を抽出し、[contracts.md](contracts.md) の条件台帳を使用する。必須条件、順位付けの希望、許容される代替案、明示された例外を区別し、範囲や判断結果を変える不足情報だけを質問する。

検証方法に応じて作業を組む：
- **サイトと一覧での一次選別**：地域、賃料と管理費、面積、階数、礼金、敷金、入居時期など、サイトが対応している項目。
- **詳細の判断**：間取り上の使用可能な空間、家具の配置、内装の質感、採光、浴室・トイレなど、説明、間取り図、写真による裏付けが必要な条件。
- **独立した検証**：ネットワーク接続、設備仕様、その他の特別要件など、物件広告以外の証拠が必要な条件。

条件は複数の段階にまたがってもよい。一覧ではまず「インターネット無料」で選別し、具体的な接続方式は後で専門的に確認する。特別条件ごとに、まず照会先、必要な証拠、合格基準を決める。[verify-special.md](verify-special.md) を参照する。ユーザーが指定していないしきい値は未設定のままとする。

分類と分類内の並べ替えルールを決める。例えばユーザーが直通を優先する場合は、所要時間の上限を満たす徒歩または乗り換え不要の経路を、乗り換えが必要な経路より優先する。より短時間の乗り換え経路は補足として扱える。ルールはユーザーの条件に基づいて決め、merge resolver に渡して一貫して適用させる。

## 範囲の設定とタスクの編成

指定地域または通勤先から対象駅の範囲を定め、利用可能な路線と徒歩圏を考慮する。この段階では範囲を見積もり、具体的なドアツードアの所要時間は物件エージェントが検証する。今回の対象サイト、駅、絞り込み後のページ範囲など、網羅すべき目標を明示する。

1. 独立した [merge resolver](merge-resolver.md) を作成し、条件台帳、並べ替えルール、網羅目標、統一文書の要件を渡す。
2. サイト別または地域別に [収集エージェント](collect-area.md) を作成し、必要に応じてサイトと地域の組み合わせに分割して、範囲、出典、重複する境界を伝える。共通条件によるサイト内の絞り込みと一覧での追加選別を並列で実行した後、バッチを直接 merge resolver に渡して重複を排除する。
3. merge resolver が出した重複排除済みの候補キューとユーザーの優先順位に従い、各物件の担当者を1人に定め、1件または少数の物件を割り当てる。同一性の確認が複雑なものや特別条件は個別に割り当ててもよい。引き継ぎは [contracts.md](contracts.md) を参照する。
4. [物件エージェント](verify-property.md) に自ら [独立した再確認エージェント](review-property.md) を作成させ、再確認で見つかった問題を処理した後、結果を merge resolver に渡させる。主エージェントは物件ごとの再確認を代行したり、項目ごとの追加調査を指揮したりしない。

既存のお気に入りリンクは、一覧での追加選別と merge resolver による重複排除へ直接進める。逆引きに適した特別条件については、事業者の導入済み建物や管理会社の設備資料から募集中の物件を逆引きする方法を補助的に加えてもよい。必要に応じて [事業者情報からの逆引き付録](appendix/provider-reverse-lookup.md) を収集担当者に渡し、共通条件の一次選別は引き続き行う。

重複排除が済んだバッチから検証を開始でき、すべての地域の収集終了を待つ必要はない。利用可能な並列処理能力に応じてリソースを配分し、物件の検証、独立した再確認、追加調査のための余裕を確保する。専門的な照会にセッション数や頻度の制限がある場合は、独立したセッションを用意するか順番に実行する。独立したエージェントを使えない場合は、その旨を明記して自己点検に切り替え、独立した再確認が完了したとは主張しない。

## 範囲、ルール、許可に関する上位判断

通常の同一性、出典、価格、結論の食い違いは、merge resolver が関連する物件担当者と調整する。単一物件の証拠不足や再確認に伴う修正は、物件エージェントとその再確認エージェントの間で処理する。

条件の意味、しきい値、証拠基準、優先順位、範囲、許可を変更する事項のみを主エージェントに上げる。既存のユーザー要件に基づいて判断し、ユーザーの選択や新しい許可が必要な場合は具体的な質問をする。物件が見つかりにくいことや資料不足を理由に、必須条件を独断で緩めてはならない。ルールの変更は影響を受ける役割に通知し、その他の有効な結果は保持する。

## 進捗と納品

各役割からの報告に基づいて、利用可能な結果、重要な阻害要因、未網羅の範囲、判断が必要な事項をユーザーに説明する。個別物件の検証を引き取らずに、随時進捗を報告できる。統合報告が不十分な場合は、物件を項目ごとに再審査するのではなく、全体の状況の補足を求める。

merge resolver は同一の統一文書を維持し、分類・並べ替えを実行して未解決事項を報告する。主エージェントはそれに基づいてユーザーに納品し、要件に関わるトレードオフと次の対応を説明する。

今回の作業の収束は合意した範囲を基準とする。収集範囲の作業が完了しているか、明確に阻まれていること。割り当て済みの全物件に結果と再確認状況があること。重複排除後の残りの候補は、それぞれ検証待ち、未検証、保留の状態と理由を明記し、未割り当てを理由に対象範囲から消してはならない。通常の食い違いが解決されているか、そのまま正直に記録されていること。統一文書が更新されていること。合意した範囲内で実行可能な検証は引き続き進める。ユーザーと合意した範囲、停止条件、または明確な阻害要因に基づいて収束させる場合は、残りの候補数（信頼できる集計ができる場合）、範囲、次の対応を納品時に開示し、未処理事項の列挙を検証完了と同一視しない。公開されている証拠で調べられる限界に達した場合は、要確認事項を残して納品してよいが、「今回の調査を完了した」ことを、すべての必須条件に合格したこととして伝えない。
