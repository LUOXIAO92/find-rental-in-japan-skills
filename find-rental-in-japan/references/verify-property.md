# 物件ごとの全項目の検証

統合担当（merge resolver）が重複を除いた後、主エージェントから割り当てられた候補を検証する。各担当者は1室または少数の具体的な部屋を受け持ち、それぞれの部屋について検証全体を独立して完了する。すべての物件を、連携しない費用班、通勤班、写真班に分けない。

## 入力と納品内容

統合担当から、物件識別子、統合の根拠とリンク、ユーザーの必須条件と希望条件、共通条件の事前絞り込み結果、通勤先と時間の要件、主エージェントが定めた特殊条件の検証計画を受け取る。

[contracts.md](contracts.md)の共通結果形式を引き継ぐ。事前絞り込みの結果は手がかりにとどめ、採用に影響する項目は詳細ページでも確認する。

各部屋について、次の項目を含む検証結果を個別に納品する。

- 識別情報と有効性、条件ごとの結論
- 費用と契約、間取りと写真の評価
- 通勤の検証結果、該当する特殊条件の検証結果
- 情報源と検索時刻、要確認事項

リンク、画像、一部の分岐の結果だけを渡さず、物件全体の結論をまとめる。未検証の必須条件は要確認として残し、合格のように見せない。

## 1. 部屋と現在の募集状況を特定する

1. 建物名と別名、完全な住所、棟番号、階数、部屋番号、面積、間取りを確認する。部屋番号が非公開なら、その部屋を区別できる項目と、識別が不確かな点を記録する
2. 重複掲載の賃料、管理費、間取り図、写真を照合する。同じ部屋と確認できない場合は、費用や根拠を統合しない。情報源間・物件間の矛盾が解決しない場合は統合担当に調整を依頼し、その部屋の担当者が引き続き追加調査する
3. 現在の広告が開けるか、掲載・更新時刻、募集状況、入居可能時期を記録する。ページが残っているだけでは、空室や申込可能であることの根拠にはならない
4. 「募集中」「空室」「入居日相談可」など、原文が示す状態を区別する。募集終了した広告を有効な推薦として扱わない
5. 入居期限がある場合は、現在の入居可能日と必要な手続き期間から期限に間に合うかを検証する。情報が足りなければ、誰に何を確認してもらう必要があるかを示す

## 2. 詳細条件、費用、契約を確認する

- 必須条件を項目ごとに再検証する。サイトで絞り込めない条件は詳細を読み、一覧に表示されていないことだけで不適合と判断しない
- 普通借家か定期借家か、契約期間、更新・再契約条件、更新料、短期解約条項を記録する。再契約の可能性があっても、継続して住める保証にはならない
- 月額費用は、賃料、管理費／共益費、明確に必須のその他月額費用に分けて記す。任意のサービスは別記し、総月額支出を賃料だけの金額として書かない
- 初期費用は、敷金、礼金、仲介手数料、保証会社費用、保険、鍵交換、清掃、その他明確に必須の項目に分ける。税額、返還条件、未見積もりの項目も記す
- 初期費用の総額は、判明している入居日、日割りルール、見積もりに基づく場合のみ計算する。欠落項目があれば、判明している費用の小計か、根拠のある概算を前提とともに示す。根拠以上に精密な総額を示さない
- 退去時清掃費、解約予告期間、適用される違約金を確認する。広告に開示されている条項と、契約書や管理側への確認が必要な条項を区別する
- 同じ項目に矛盾があれば、情報源、日付、相違点を残す。安い費用や緩い条件をつなぎ合わせ、実在しないプランを作らない

## 3. 間取り、実写、住み心地を確認する

1. 実際の間取り図と入手できる室内写真を見て、元のページに戻れるリンク、画像番号、その他の位置情報を記録する。画像を見ていなければ、視覚的な評価をしない
2. その部屋の実写、同じ建物の別室、同じ間取りの参考写真、モデルルーム、完成予想図を区別する。参考写真は、その部屋の内装状態の根拠にはならない
3. ユーザーの基準に沿って、部屋の形状と使える壁面、家具の配置、キッチンと居室の関係、光を遮るもの、収納、設備、目で確認できる老朽化の程度などを判断する
4. 観察した事実と主観的な評価を区別し、判断の根拠を書く。「新しい」「きれい」「広い」といった言葉を具体的な根拠の代わりにせず、写真から分からない防音性や臭いも推測しない。内装の質感や古びて見えるかなど、定性的な条件は実写と詳細情報を合わせて判断する。築年、改装年、「リフォーム済」などの表示は手がかりにすぎず、それだけで現在の室内状態を証明することはできない
5. 図面と写真が一致しない、写真の角度が不十分、重要な空間の写真がない場合は、どの判断に影響するかを記す。追加で必要な写真や現地での確認事項も示す

## 4. ユーザーの利用場面に合わせて通勤を検証する

- 建物入口付近からユーザー指定の目的地入口まで、指定された平日と出発／到着時間帯で経路を検索する。同じ条件で検索を再現できるようにし、住所が不完全な場合は位置特定の精度を記す
- ドア・ツー・ドアの総所要時間、出発地・到着地の徒歩区間、乗車区間、乗り換え回数、経路検索リンク／時刻を報告する。待ち時間と駅構内の乗り換え時間を含むか説明し、二重に加算しない
- 広告の「駅徒歩何分」は手がかりにとどめる。最寄り駅から目的駅までの乗車時間を、通勤の総所要時間の代わりに使わない
- 直通が必須、または乗り換えが少ないことが希望の場合は、実際に列車を乗り換える必要があるかを確認する。相互直通運転と同じ駅での乗り換えを分けて説明する
- 候補は同じ時間基準で比較する。運行便、出入口、位置特定の不確実性による誤差は推定として残し、経路案内の所要時間を保証された値として書かない

## 5. 特殊条件を検証し、物件全体の結論をまとめる

ユーザーに特殊条件がある場合のみ[verify-special.md](verify-special.md)を読み、主エージェントが示した検証計画を実行する。ツールが使える場合は、互いに独立した確認を範囲を限定して並行委任してよい。委任後も、その部屋の検証担当者が識別情報の照合、根拠の集約、物件全体の納品内容の補完を担当する。

共通形式に従って合格、不合格、要確認の項目を示し、採用に影響する理由と、次に必要な最小限の対応を書く。必須条件への不適合が明確な根拠で確認できた場合は、意思決定に役立たない後続の確認を中止してよい。続行しなかった範囲を記録し、検証全体が完了したように装わない。

## 6. 再確認エージェントを自ら作成し、修正後の結果を納品する

物件全体の初回調査が終わったら、次の順に独立した再確認と修正を進める。

1. 物件エージェント自身が、現在使える並行処理機能で独立した再確認エージェントを作成する。[review-property.md](review-property.md)と、[contracts.md](contracts.md)で定める再確認用入力を渡す。元のユーザー要件、調査した事実、情報源を先に示し、暫定結論は別記する。決めておいた結論の承認を求めたり、分担した専門的な確認を、物件全体の独立した再確認と見なしたりしない
2. 「問題／証拠／必要な対応／状態」を受け取ったら、自ら追加調査や修正を行う。同じ再確認エージェントに、影響を受ける部分を再確認してもらう。通常の事実の矛盾は、統合担当が関係する担当者を調整する。条件、基準値、検証方法、範囲、承認の変更が必要な場合は主エージェントに判断を求め、勝手に緩和しない
3. 公開情報の限界に達した場合は、再確認エージェントとともに不明点を明示して取りまとめてもよい。欠落項目、適合性への影響、最小限の確認質問を残す。不足を合理的に追加調査できる場合は続行する
4. 情報源にアクセスできない、確認範囲が限られる、追加調査できる問題が未解決であるといった状況は、すべて正直に記録する。再確認に合格したと偽らない。独立したエージェントを使えない場合は自己点検を行い、「自己点検のみ、独立した再確認は未実施」と明記する
5. 修正済みの物件全体の調査結果、再確認状態、未解決事項を[統合担当](merge-resolver.md)に渡し、統合、並べ替え、文書の維持を任せる。主エージェントには進捗や判断が必要な事項を報告すればよく、住戸ごとの再確認を求めない

新たな根拠が既存の結論に影響した場合は、物件エージェントが追加調査と影響部分の再確認を担当し、その後に差分を納品する。
