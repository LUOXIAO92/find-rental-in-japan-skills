# 用户特殊条件核验

只在本次需求包含普通网站筛选或详情阅读无法可靠判定的条件时读取本文件。特殊条件由本次用户需求决定，不内置某个城市、期限、运营商或生活偏好。

## 主agent先确定查法

在分配具体房源前，对每项特殊条件明确以下内容，并随房源任务下发：

- 用户到底要求什么：硬条件还是偏好、作用于整栋还是具体房间、可接受阈值与例外
- 要核实的事实及通过条件；用户用语有多种会改变筛选结果的含义时，先问清关键含义
- 能回答该问题的来源和方法：例如运营方查询、管理方书面说明、图纸或现场测量，及各自能证明的范围
- 哪些证据足够通过、哪些足够排除、哪些只能记为待确认；是否必须相互印证
- 可以并行的独立查询及其输入、输出；需要用户或主agent补充的信息和需要另行授权的动作

先设计可执行的核验方案，再要求各房源核验者执行。不要只下发“确认条件满足”，把判断标准留给不同核验者自行猜测。方法或证据标准需要改变时升级主agent；按既定方法查证、复核和解决普通事实差异无需主agent逐项介入。

## 房源核验者执行

1. 将每条证据绑定到本栋、本房间和对应条件；同名楼、邻栋、附近设施或其他房间的证据不能直接移用
2. 按方案查询当前信息，保留来源、查询日期、对象范围与关键原文；广告措辞和销售宣传不能替代所需的技术或合同事实
3. 有可用工具且任务彼此独立时，可把某项有界检查交给子代理，例如查一个楼栋的官方可用性；交代已确认身份、问题与证据标准
4. 委派后仍由本房源核验者检查身份匹配、整合证据及补查；跨来源或跨房源的未决事实冲突交merge resolver协调。不能用“分支说可以”替代证据，专项分支不代替房源agent自行创建的整套独立复核
5. 查询入口不可用或公开资料不足时，尝试适合该问题的其他来源；仍无结论就列出最小待确认问题及应回答的对象
6. 如需联系管理方、提交信息或申请服务，向主agent说明具体对象、动作及所需授权；公开查不到不等于允许代用户申请

## 判断与回传

- 通过：证据覆盖用户定义的全部必要条件；结论不超出证据适用的楼栋、房间、时间或服务范围
- 不通过：可靠证据明确违反硬条件，指出失败项；不要把查询无结果当作不可用
- 待确认：地址匹配不确定、关键字段缺失、证据冲突或只能证明部分条件，写明缺什么才能完成判断
- 偏好：单列符合程度及理由，不擅自升级为淘汰条件，也不以偏好优点抵消硬条件失败
- 专项分支使用 [contracts.md](contracts.md) 的共同格式回传房源负责人；负责人将证据纳入整套结果，交其独立复核agent检查，修正后交merge resolver。最终结果保留未解决的特殊条件
